## 2. Mobile

- Нижняя **фиксированная панель**: цена от, ближайшая дата, «Оставить заявку», подстрочник про ответ организатора.
- Sticky rail не дублировать с панелью.

---

## 3. Порядок блоков: текущее → целевое

| Приоритет ТЗ | Сейчас (порядок в коде) | Целевое изменение |
|--------------|------------------------|-------------------|
| Decision-first сверху | Hero + CTA есть; нет рейтинга в hero; нет микротекста под CTA | Добавить рейтинг/отзывы в summary; микротекст; компактный details сразу под hero |
| Отзывы сильнее | Отзывы и UGC внизу | Поднять блок отзывов выше (после itinerary или после «для кого/риск» — решение прототипа; минимум — сразу после details) |
| Включено/не включено | Есть, одна секция | Две колонки, короткие строки (возможно парсинг списков из API) |
| Программа по дням | `itineraryDayByDay` как prose | Структурированный аккордеон по дням (данные: миграция контента или новое поле) |
| Sticky CTA | Нет | Новый компонент |
| «Почему можно доверять» | Есть как `trustReason` | Переименовать в нейтральное («О чём говорит карточка» / факты без обещания платформы) |

---

## 4. CTA и формулировки (ТЗ §3.2)

- Основной CTA: **«Оставить заявку»** или **«Отправить заявку организатору»**.
- Не использовать как основной: «Забронировать», «Купить», «Подтвердить участие» до реализации сценария.

---

## 5. Приёмка wireframe PDP

- [ ] Без скролла на типичном laptop видны: название, регион, даты, длительность, дисциплина, тип/формат, цена, рейтинг/отзывы (или нейтрал.), CTA, микротекст под CTA.
- [ ] Нет визуального слияния «платформа = организатор поездки».
- [ ] Нет запрещённых платформенных обещаний; верификация — как **статус данных**, не «надёжный организатор».
- [ ] Sticky CTA на desktop + bottom bar на mobile.
