# MyWaveTour: проверка готовности и первый шаг Mini App

Дата: 2026-10-03. Область: MyWaveTour / Turism, не MyWave Event App.

## Цель и порядок

1. Зафиксировать текущий production и состояние веток, не смешивая незакоммиченные изменения.
2. Проверить публичные страницы без записи в production; формы — только в отдельной локальной БД.
3. Реализовать одну цель: список поездок и фильтры внутри существующей страницы `/dates` / Telegram Mini App.
4. Проверить unit/integration, сборки, Docker и мобильный браузер.
5. Зафиксировать отдельные блокеры подписок и дизайна. Не считать их устранёнными этим изменением.

## Что реализовано

- Список поездок на `/dates`, без обязательного перехода в основной каталог.
- Совместные фильтры по дисциплине, уровню и дате старта. Счётчик, календарь и список используют одинаковую выборку.
- Порционная загрузка отображения: 6 → 12 → все результаты; это не лимит доступных программ.
- Честные состояния загрузки, пустой выдачи, ошибки и повторного запроса; таймаут 20 секунд.
- Обработка Telegram `start_param`, query/hash `tgWebAppStartParam`, явных дат и фильтров.
- Дата из API не сдвигается на предыдущий день при UTC-полуночи. Календарь монтируется на клиенте, чтобы не расходиться с SSR по часовому поясу.
- Переходы к карточке/заявке и полному каталогу открывают сайт отдельно; сохраняются обе даты, фильтры и UTM, но не Telegram auth data.
- Используются существующие media/обложки и fallback. Новые изображения и вымышленные фото реальных поездок не добавлялись.
- Никаких новых миграций, зависимостей, портов production или изменений Compose.

## Блокеры и ограничения — не устранены в этом PR

### P1: обещание уведомления о новых поездках пока не готово

1. `services/api/src/modules/subscriptions/routes.ts`: проверяется только `consent === false`; отсутствие поля принимается. В sandbox запрос без consent вернул 201 вместо 400.
2. После создания subscription её `metaJson` заменяется объектом note; SQL в sandbox показал потерю consent/source/utm. Согласие должно сохраняться, а не подразумеваться.
3. `notifier.ts` отправляет личное сообщение через `chat_id=@username`. Для личного чата нужен подтверждённый числовой chat ID после `/start`.
4. API создаёт ссылку `mywave_sub_<id>`, но обработчик привязки этого start payload не найден. В модели отсутствуют фильтры по уровню/выбранному диапазону и подтверждённый Telegram chat ID.

Поэтому пункт «сообщить, когда появится поездка» не отмечен выполненным. Нужен отдельный backend PR: явное согласие, сохранение metadata, привязка чата по одноразовому payload, фильтры, idempotent delivery и отказ от повторных отправок. До его приёмки не обещать Telegram-доставку.

### P1: текущая дедупликация скрывает разные программы

Повторный read-only вызов API: 151 запись; существующий `dedupeProgramListingsByEvent` оставляет 113. Его loose key не использует название или `scheduleType`: один организатор + одинаковые placeholder-даты/длительность/регион становятся «одним событием».

Например, исчезают разные `on_request` программы БЕАРТРО: Начикинское озеро, Вачкажец, снегоходная экскурсия к Авачинскому вулкану и культура коренных народов. Это не доказанные дубли. Требуется отдельный регрессионный фикс сигнатуры, прежде чем утверждать «показаны все актуальные программы».

Новый Mini App повторно использует текущую дедупликацию, но намеренно показывает только подтверждённые даты старта; `on_request` остаются в полном каталоге. Не превращать placeholder-даты в реальные даты выезда.

### P2 / отдельная приёмка

- Production обещает «по России», но каталог содержит зарубежные регионы. Нужна согласованная география продукта, не молчаливое удаление данных.
- На homepage однократно зафиксирована React hydration error 418. Исправлена защита календаря `/dates`, но причина homepage отдельно не устранена.
- На выборочной карточке гонки виден тип «Кэмп» и технический alt media. Это вопросы нормализации контента; сравнение каждой карточки с источником не проводилось.
- Не проверены реальные SMTP/Telegram-доставка, оплата/refund, все административные роли, все original media URL и Instagram session/proxy. HTTP 200 и unit tests не заменяют эти сценарии.
- Изменённый Mini App ещё не проверен внутри реального authenticated Telegram WebView: MainButton, haptic, safe area, возврат из карточки и Android/iOS.

## Как воспроизвести

PowerShell из корня ветки:

```powershell
pnpm install --frozen-lockfile
pnpm run test:mini-catalog
pnpm run test:web:ux
pnpm run check:quality
node scripts/qa/tourism-public-readiness.mjs https://mywavetour.ru
docker build -f apps/web/Dockerfile -t tourism-miniapp-qa-web:local .
```

Публичный smoke только читает данные. Локальный acceptance **создаёт** QA-записи и разрешён исключительно с отдельно подготовленной disposable БД/API:

```powershell
node scripts/qa/tourism-local-acceptance.mjs http://127.0.0.1:3001
```

Его текущий exit 1 — подтверждённый subscription consent defect. Не запускать against production; guard отклоняет не-loopback hostname. Нельзя направлять локальный API на production DB.

Перед deploy: зелёный CI на точном SHA PR, проверка действующего API contract и оригинальных media на dated-карточках, приёмка authenticated Mini App, проверка `/dates` CSP/Telegram frame-ancestors. Никаких переключений webhook/polling для frontend-функции не нужно.

## Риски, rollback и следующий шаг

- Риск: загрузка всего публичного API и текущая global-dedupe semantics. Сохранены текущие API contract и media helpers; лимит отображения не обрезает выборку.
- Rollback: revert frontend/тестового PR и обычный предыдущий web artifact. БД/env/Compose откатывать не требуется.
- Следующая логическая цель: subscriptions backend и полнота каталога — отдельные PR. Дизайн первого экрана рассматривается отдельно, после согласования макета, без массовой смены UI.
