# G4 — внутренняя перелинковка + усиление конверсии

**Статус:** план (после закрытия G3.2)  
**Предпосылки:** G1–G3.2 (блог, подборки, SEO-хабы `/explore`, UTM-задел) реализованы.  
**Связанные документы:** [CONTENT_EXPLORE_HUBS_ADR.md](CONTENT_EXPLORE_HUBS_ADR.md), [CONTENT_PIPELINE_DATA_MODEL.md](CONTENT_PIPELINE_DATA_MODEL.md).

## 1. Цель продукта

| Метрика смысла | Формулировка |
|----------------|--------------|
| Пользовательский путь | `контент (blog / collection / explore) → программа → заявка` |
| Навигация | Пользователь **не остаётся в тупике**: с любой витринной страницы виден «следующий шаг» (каталог, хаб, похожее, CTA) |
| Измеримость | Понятно, **какой вход** (blog / collection / explore) ведёт к кликам и заявкам |

## 2. Архитектура (без лишних сущностей)

**Принцип:** не вводить новую «сущность графа» в БД в G4.0. Источник истины остаётся в уже существующих полях:

- `blog_posts`: `discipline`, `region`, `tags`, `relatedProgramIds`, …
- `content_collections`: оси + `related*Ids`
- `programs`: `discipline`, `region` + публичная видимость
- **Explore:** `rawStringToHubSlug` + `MANUAL_EXPLORE_HUBS` → стабильные ссылки `/explore/{type}/{slug}`

**Слой G4 = вычисляемые ссылки + UI-блоки** (server components / небольшие API-надстройки), опционально — лёгкие DTO в ответах `GET /public/...` (например `suggestedExploreLinks: { type, slug, label }[]`), без обязательной миграции.

**UTM / entry (развитие G3):** единые правила: `utm_source` ∈ { `blog`, `collection`, `explore` } + идентификаторы (`blog` — slug/post id в query по мере согласования; уже есть `collection_id`, `explore_type`/`explore_slug`).

## 3. Пакеты работ (по приоритету)

### P0 — критично для «нет тупиков»

| # | Задача | Почему влияет на конверсию |
|---|--------|----------------------------|
| 1 | **Блог → Explore:** в сайдбаре/низу статьи — ссылка на релевантный хаб, если `discipline`/`region` маппится в существующий `/explore/.../...` (через тот же словарь, что API) | Поисковый/контекстный переход к каталогу по теме |
| 2 | **Explore → блог/подборки:** на странице хаба усилить блоки (уже есть списки) + явные CTA «все статьи по теме» (якорь/фильтр) | Удержание и доверие |
| 3 | **Program PDP → Explore:** ссылка «Смотреть направление X» / «Другие программы в регионе» (1–2 ссылки max) | Возврат в широкий воронку без «застревания» на одной программе |
| 4 | **Collection → Explore:** при совпадении `discipline`/`region`/`season` с хабом — ссылка «Смотреть все материалы по теме» | Согласованность кураторской и автоматической витрины |

**Реализация:** в `apps/web` — маленькие pure-функции `buildExplorePathFromPost(post)` / `fromProgram` / `fromCollection` (дублировать **минимально** логику с API или вынести в `packages/shared` тип `resolveExploreLink` — решить в задаче).

## 4. Критерий готовности G4.1 (MVP G4)

1. С трёх типов страниц (**blog post**, **program**, **collection**) есть **≥1** осмысленная ссылка на **explore** (где применимо по данным).  
2. С **explore** — явные CTA в каталог / заявку (уже частично есть) + блок «не тупик» (см. P0).  
3. UTM не ломают существующие; новые ссылки согласованы с `buildExploreUtmQuery` / `buildCollectionUtmQuery`.  
4. Документ этот + короткое обновление `CONTENT_PIPELINE_DATA_MODEL` после внедрения.

## 5. Риски

| Риск | Митигация |
|------|-----------|
| Расхождение web/API в slug хаба | Один хелпер + тесты на `freeride` и `MANUAL` |
| Перегруз ссылками | Max 2–3 перелинковки на видимом экране |
| Сезонные хабы с пустыми списками | Не трогать в G4 как «баг» (G3.2 соглашение) |

## 6. Зависимости

- G3.2 explore API и словарь — **без изменения контракта** для P0, если не добавлять DTO.  
- Admin не обязателен для G4.1 (всё вычисляемое).

**Итог:** G4 превращает уже существующую контентную систему в **связанный вороночный опыт** и готовит измеримость заявок по каналу входа — без big-bang рефакторинга.

## 7. G4.1 — baseline (зафиксировано)

### 7.1 CTA (копирайт)

Текущие формулировки CTA на **blog, collections, program PDP, explore** приняты как **baseline** для последующих экспериментов (A/B — позже, после сбора данных). Правка без изменения вёрстки, акцент на action-oriented + микро-тексты снижения барьера; формулировка «оставить заявку» **не** используется на этих витринах.

### 7.2 Трекинг заявок по входу

- При создании `POST /bookings` в `sourceCampaign` пишутся `entry_type`, `entry_id`, `utm_*`, при explore — `explore_type` / `explore_slug` (pipe-строка); в `notes` дублируется блок `[tracking] …` для читаемости.
- **Отчёт (админ, без миграции):** `GET /metrics/content-entries?from=…&to=…` (авторизация admin) — агрегат по паре `entry_type` + `entry_id` за период. UI: **Аналитика → Content entries** в админке.
- **Интерпретация «без трекинга»:** прямые заходы на PDP, старые заявки до G4.1, нестандартные ссылки.
