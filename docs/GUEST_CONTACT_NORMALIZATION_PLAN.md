# План нормализации guestContact (безопасный)

## Текущее состояние (MVP)

- **guestContact** — одна строка (single string). Допустимо для MVP: контакт гостя в свободной форме (телефон, email, "Иван +7…", "Telegram @user" и т.д.).
- Валидация: наличие непустой строки при создании бронирования.

## Цель нормализации

Разделить на структурированные поля для:
- корректной коммуникации (email для писем, phone для звонков/SMS);
- соблюдения правил хранения персональных данных;
- единообразия отображения в админке и отчётах.

## Предлагаемые поля (следующий этап)

| Поле           | Тип    | Обязательность | Комментарий                    |
|----------------|--------|----------------|--------------------------------|
| guestName      | string | опционально    | Имя гостя                      |
| guestPhone     | string | опционально    | Нормализованный телефон        |
| guestEmail     | string | опционально    | Email                          |
| guestTelegram  | string | опционально    | Telegram (id или @username)    |

**Ограничение:** минимум один из контактов (phone / email / telegram) должен быть заполнен при создании заявки.

## Безопасный порядок внедрения

1. **Добавить новые поля в схему** (nullable), оставив `guestContact` как есть.
2. **Миграция данных не обязательна** — старые заявки продолжают хранить контакт в `guestContact`.
3. **API intake (POST /bookings):**
   - принимать и `guestContact` (как сейчас), и опционально `guestName`, `guestPhone`, `guestEmail`, `guestTelegram`;
   - если переданы структурированные поля — сохранять их и при желании конкатенировать в `guestContact` для обратной совместимости или оставить `guestContact` пустым/автозаполненным.
4. **Админка:** показывать и редактировать оба варианта (одну строку и/или разбитые поля).
5. **Постепенно:** новые заявки заполнять только структурированными полями; через N спринтов объявить `guestContact` deprecated и при необходимости убрать после миграции старых записей.

## Риски и митигация

- **Дублирование данных:** один источник истины для отображения — либо `guestContact`, либо конкатенация полей (решить в конфиге/логике).
- **Персональные данные:** не логировать полные контакты в audit; в отчётах — маскирование (например, +7***123-45-67).
- **Валидация:** формат телефона/email — опциональная нормализация на бэкенде; при несоответствии — сохранять как есть в одном из полей, не блокируя intake.

## Source of truth

- Текущий MVP: **booking.guestContact** (single string).
- После нормализации: **booking.guestName, guestPhone, guestEmail, guestTelegram** с fallback на **guestContact** для старых записей.
