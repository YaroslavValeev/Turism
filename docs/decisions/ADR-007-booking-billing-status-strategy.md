# ADR-007: Стратегия Booking status vs Billing (payment-derived)

## Статус

**Accepted** (2026-04-17) — зафиксирован **вариант C** (двухконтурный контракт). Реализация Stage 4.1: `deriveBookingStatus` вынесен в `services/api/src/modules/billing/deriveBookingStatus.ts`; новые писатели `bookingStatus` без ADR запрещены.

## Резолюция к принятию (рекомендация Product Logic)

**Рекомендуется принять вариант C** как целевой для Stage 4.1.

**Почему:**

- Уже реализованы доменные события `booking_payment_derived_status` и операционный граф booking — формализация **двухконтурного контракта** даёт управляемость без Big Bang миграции и без блокировки платежей из‑за несовпадения графа «воронка» и «деньги».
- Вариант A требует либо расширения `bookingTransitions` под все финансовые пары, либо частых отказов engine — высокий риск регрессий при одиночном разработчике/узкой команде.
- Вариант B (отдельное поле под settlement) — правильный возможный следующий шаг, но это миграция схемы и всех потребителей; разумно вынести **после** стабилизации контракта C и метрик конфликтов.

**После Accepted:** зафиксировать в коде и доках правило «только два паттерна смены `bookingStatus`» (engine vs billing+событие); опционально вынести `deriveBookingStatus` в отдельный модуль для ясности; не добавлять третьих писателей без ADR.

Эволюция к A или B — отдельный ADR при появлении измеримых конфликтов или требований отчётности.

## Контекст

Сейчас сосуществуют:

1. **Операционный lifecycle** заявки: граф `bookingTransitions` в `@mywave/shared-policy`, исполнение через `applyBookingStatusTransition` (ручной PATCH, доставка lead).
2. **Платёжно-учётный контур**: `billing/service.ts` пересчитывает суммы и выставляет `bookingStatus` через `deriveBookingStatus` (`created` / `paid_full` / `refunded_*` и т.д.), плюс доменное событие **`booking_payment_derived_status`**.

Это **два контура одного поля** `Booking.bookingStatus`. Они не противоречат друг другу случайно только пока объём сценариев ограничен; при расширении возможны коллизии и неочевидная семантика для отчётов и UI.

## Варианты решения (на выбор)

### Вариант A — Единый источник: billing вызывает booking engine

- При изменении сумм billing **не** пишет `bookingStatus` напрямую.
- Вычисляется целевой статус `next`; если `isValidBookingTransition(current, next)` — вызывается `applyBookingStatusTransition` с `triggerMode: "auto"`, `actorMarker: system:billing`.
- Если переход по графу **невозможен** — требуется явная политика: либо промежуточные ручные шаги, либо расширение графа под финансовые переходы (отдельное решение).

**Плюсы:** один механизм событий/audit для смены статуса. **Минусы:** возможны блокировки, пока граф не покрывает все финансовые пары состояний.

### Вариант B — Два смысловых слоя (явная декомпозиция)

- Поле `bookingStatus` остаётся **операционным** (воронка организатора/платформы).
- Вводится отдельное поле или материализованное представление **`settlementStatus` / `paymentLifecycle`** (или только доменные события без поля), куда пишет billing.
- UI и отчёты знают, какой слой показывать.

**Плюсы:** нет ложного смешения воронки и денег. **Минусы:** миграция схемы и всех потребителей `bookingStatus` как «единого статуса».

### Вариант C — Оставить как есть, формализовать контракт (минимум на Stage 4.1)

- Сохранить текущую запись `bookingStatus` из billing.
- В ADR и в коде зафиксировать: **`booking_payment_derived_status`** — каноничный след платёжного контура; операционные переходы — каноничный след PATCH/доставки.
- Запретить новым модулям менять `bookingStatus` без записи в одном из двух паттернов (engine или billing+событие).

**Плюсы:** минимальная стоимость. **Минусы:** два контура остаются до следующей волны рефакторинга.

## Рекомендация архитектора (не финальная)

Сначала зафиксировать **вариант C** как явный контракт (1–2 дня), затем эволюция к **A** или **B** по метрикам конфликтов и требованиям отчётности.

## Последствия

- **Закрытый контур:** менять `bookingStatus` могут только (1) операционный engine и (2) billing + событие `booking_payment_derived_status`. Список прямых записей — `docs/migration/STAGE4_1_DIRECT_STATUS_WRITES.md` (только **сужается**, не расширяется без явного решения).
- QA Stage 4.1: сценарии «ручной переход + платёж» и «платёж + ручной переход».
